# Sigma 编辑器操作架构与职责边界

记录日期：2026-11-06。

本文记录编辑器操作层的架构整理方向。它是目标设计与渐进迁移依据，不代表相关能力已经实现，也不构成全面重构的执行授权。

## 1. 核心判断

当前问题不是整个架构错误，而是底层模块已经拆开，上层操作尚未形成统一的职责归属：文件分了层，职责没有完全分层。

即使不接入 AI，也值得整理这些边界。AI 接入只是让已有问题更明显，不是问题产生的原因。

首先需要的是正常编辑器本来就应该有的编辑操作层，而不是单独建设一套 AI 操作层。UI、快捷键、画布手势与未来的 AI 都应成为同一套编辑能力的调用方。

## 2. 现状中的职责问题

### 2.1 完整操作散落在不同位置

当前几何面板先调用 `DesignGeom.setGeom()` 修改文档，再由 React 组件调用 `undo.track()`；鼠标创建流程则由 `StageCreate` 组织几何计算、节点创建、父子关系、选择和历史。

这些都是编辑操作，但没有一致的总负责人。调用方必须了解每个方法是否已经开启事务、维护选择或记录历史，增加了组合操作时漏记、多记与行为不一致的风险。

### 2.2 操作目标隐式依赖当前选区

填充、描边、删除等能力依赖 `Select` 读取目标。它适合按钮调用，却不利于批量操作与程序调用。

修改节点 B 不应要求先把用户选区切换到 B。选区是操作目标的一种来源，不应成为文档修改的隐含前提。

### 2.3 实例作用域与全局状态混杂

`Editor` 已按实例组织服务，但文档查询仍经过模块级可变的 `docGetter`；Global 的 `FileAction` 也依赖部分编辑器服务。

这会模糊文档身份与生命周期。读取和写入应绑定明确的编辑会话，文件管理不应意外持有另一套选择、撤销和编辑文档实例。

### 2.4 操作、交互与展示的边界不一致

`Command`、`NodeAction`、`Design*` 和 `Stage*` 有的表达用户意图，有的执行数据修改，有的组织交互，还有的同时承担多种职责。

问题不在名字，而在不同模块都可能成为一次编辑操作的总负责人。现有菜单与快捷键 `Command` 不能直接等同于稳定的程序操作接口。

## 3. 目标结构

将“怎么触发”和“做什么”分开：

```text
React 面板 / 快捷键 / 画布手势 / 未来的 AI
                      ↓
                 编辑操作层
                      ↓
            文档模型与底层修改能力
                      ↓
             文档变化 → 渲染更新
```

编辑会话负责组织各项状态和生命周期：

```text
编辑会话（现有 Editor / Session，名称不预先强制调整）
├─ 文档
├─ 选择、视口、当前工具
├─ 历史与操作执行
└─ 渲染、资源和生命周期
```

这是职责划分，不要求每一层对应一个新类或新包。优先复用现有服务与类型明确的方法，不先建设庞大的命令框架、注册中心或事件总线。

## 4. 各层职责

| 层                 | 负责                                               | 不负责                               |
| ------------------ | -------------------------------------------------- | ------------------------------------ |
| 输入与交互         | 收集意图、手势计算、驱动临时预览                   | 自行决定文档操作如何归档历史         |
| 编辑操作           | 明确目标、校验、组合修改、提交边界、历史归档与结果 | 依赖按钮挂载、鼠标事件或隐式当前选区 |
| 文档模型与修改规则 | 默认值、节点结构关系、几何和属性规则               | 控制界面、读取当前选区               |
| 数据与历史基础设施 | Yjs 写入、patch、撤销机制                          | 理解创建卡片等业务意图               |
| 渲染               | 消费文档与视图变化，完成绘制                       | 反向成为一般文档修改的必经入口       |

历史基础设施提供机制；编辑操作层决定一次用户意图对应怎样的历史边界。

## 5. 读取、创建、修改与历史

### 5.1 读取

提供绑定会话的页面、选区、指定节点与子树查询。明确查询范围、节点身份、坐标约定及文档版本，避免每次输出整份文档。

读取不能隐式修改文档或选择。返回可序列化的数据，不暴露可用于绕过操作层写入的内部引用。

### 5.2 创建

不同输入方式只负责产生创建意图：

```text
画布手势：根据拖动得到位置和尺寸
属性面板：根据输入得到位置和尺寸
AI：根据描述得到位置和尺寸
                      ↓
         createNodes({ parentId, nodes })
                      ↓
校验 → 创建对象 → 挂载关系 → 提交历史 → 返回节点 ID
```

以上方法名仅示意职责，不是已经确定的接口签名。

复用 `DocCreator` 生成默认对象，复用 `DocMutator` 维护节点与父子关系。调用方不必自行拼装这些步骤。

创建后是否选中，应由明确的操作编排决定；底层创建函数不能偷偷改变选择。需要同时恢复文档与选择时，应明确使用对应的历史边界。

### 5.3 修改

修改以明确的节点 ID 和允许属性为输入，例如 `updateNodes({ ids, changes })`。UI 可以传入当前选区的 ID，但操作本身不依赖选区。

优先复用几何字段已有的 `supports / read / apply` 组织方式，以及节点尺寸、路径与矩阵的既有修改规则。不能为了接口方便直接写任意路径，从而绕过领域约束。

外部输入需要运行时校验，不能仅依赖 TypeScript。明确坐标空间、属性支持范围、合法数值与错误行为；不支持的属性不能静默当作成功。

### 5.4 历史

一次性操作由统一提交边界记录历史；批量操作整体形成一次历史，无实际变化不产生空历史项。

底层修改方法不自行归档，完整编辑操作也不要求 React 调用方额外补记。迁移时逐项清除重复归档，避免同时保留两套负责人。

正常撤销针对本地历史顶部，不等于可以在任意后续操作之后精准撤销某次 AI 调用。第一阶段不承诺选择性撤销。

## 6. 连续交互与一次性操作

拖动、缩放、旋转和连续输入不能每一帧都提交一条完整历史，应明确交互生命周期：

```text
开始交互 → 连续预览更新 → 结束时归档一次
                        → 取消时恢复
```

一次性操作与连续交互复用相同的文档修改规则，但采用不同的提交生命周期。手势层负责计算过程，编辑操作层负责操作边界；不要为复用而强行将两者实现为同一个入口。

异步资源准备在提交前完成，并在实际提交时重新核对目标会话和版本。不能把异步等待包进同步 Yjs 事务就认为具备完整操作语义。

## 7. 三种边界不能混淆

以下概念需要分别设计：

1. **Yjs 事务**：组织数据变更与通知，不自动提供失败回滚。
2. **一次撤销**：规定历史分组，不代表失败过程中从未暴露部分修改。
3. **业务原子性**：一组操作整体提交或不应用，需要额外保证。

现有 `YPlain.transact()` 没有失败回滚机制；外层增加 `try/catch` 也不会自动恢复文档。

第一阶段应完整预检批量输入、目标、父子关系及批内引用。恢复方式写在 `docs/editor-operation-upgrade.md`：一次用户意图进入唯一的 `execute`，失败时只撤销这次意图自己的捕获，不用整份旧文档覆盖。不能用全量旧快照覆盖来回滚协作中的他人修改。

## 8. 最小公共操作边界

第一阶段只覆盖四类能力：

- `read`：读取页面、选区、节点。
- `create`：创建并挂载 frame、rect、text。
- `update`：修改上述节点的基础几何、文本和填充属性。
- `history`：读取撤销状态、撤销与重做。

写入绑定明确会话，核对读取后是否出现文档变更。结果至少包含实际目标 ID、是否变化、修改后版本、历史状态与具体错误。

文档提交成功、资源就绪与画布完成绘制是不同结果，不用“写入成功”冒充视觉验证通过。WebMCP 或普通 MCP 只是这套能力的外部适配层，不直接操作底层 Yjs 或另写业务逻辑。

## 9. 保留与迁移

### 保留的基础

- `DocCreator` 的默认值生成。
- `DocMutator` 的结构修改能力。
- 几何字段的 `supports / read / apply` 定义。
- YDoc / YPlain 与现有历史基础设施。
- 渲染树、绘制管线和几何内核。
- 按 Editor 实例组织服务的方向。

### 渐进顺序

1. 明确会话读取与操作目标，避免新增全局文档依赖。
2. 贯通 frame、rect、text 的创建、修改和历史边界。
3. 将涉及的 UI、快捷键与手势逐步接入，保持原行为。
4. 明确批量执行、失败处理、连续交互和结果回执。
5. 最后接入 WebMCP 或 MCP，作为新的调用方。

不为了本次整理全面改名、搬目录、抽包或重写所有交互；不同时推进多编辑器格式互转或通用插件平台。

## 10. 架构验收问题

> 不挂载 React、不模拟鼠标、不偷偷切选区，能不能完成一次明确的编辑，并得到正确的历史和结果？

还应能够说明：

- 修改的是哪一个会话、哪一个版本、哪些节点？
- 谁负责参数和结构校验？谁负责历史归档？
- 连续操作何时开始、提交或取消？
- 批量执行失败后，文档处于什么状态？
- 返回的是数据提交结果，还是已经确认的绘制结果？

这些边界清楚后，AI 只是增加一个调用方，而不是再造一套编辑器。
